03 · INFORMATION BOUNDARIES

三类信息，三种生命周期

不要让 Intent、Wiki 和工程规格争夺同一份内容的“唯一真相”。

CHANGE CONTEXT

Intent

WHY

变化的业务意图

  • 问题与期望结果
  • 范围、约束、影响域
  • 开放问题与决策

生命周期：提出 → 审批 → 实现 → 归档

SYSTEM CONTEXT

Knowledge / Wiki

WHAT

长期系统知识

  • 领域模型与业务规则
  • 架构、术语、数据字典
  • ADR、运维与排障知识

生命周期：持续演进，由领域 Owner 维护

DELIVERY CONTEXT

Engineering Specs

HOW

本次如何实现

  • Spec、Plan、API / Schema
  • 测试与验收用例
  • PR、发布与实施记录

生命周期：随变更产生，保留为工程历史

边界原则：Intent 是 Change 的上下文；Knowledge 是 System 的上下文；Spec 是 Delivery 的上下文。

04 · INTENT GRANULARITY

一个 Intent，不等于一个 Jira Ticket

以“可独立解释、决策和验收的业务变更”为主要粒度，而不是按开发任务或代码提交拆分。

LEVEL 1

Initiative

战略目标 / 大型业务项目

例：建设统一订单履约体系

可跨多个业务域，持续数月

LEVEL 2 · DEFAULT

Capability / Change

可独立验收的业务变更

例：支持拆单、部分发货、物流轨迹查询

建议作为主要 Intent 粒度

LEVEL 3

Engineering Tasks

具体工程执行项

例：增加 API、调整 Schema、补充测试

通常关联 Intent，不单独创建 Intent

适合独立 Intent

有独立业务目标、验收标准、决策边界，或跨多个系统 / 团队。

通常不需要独立 Intent

纯 UI 微调、字段改名、普通缺陷、单一实现任务。重大事故整改例外。

05 · TARGET INFORMATION ARCHITECTURE

按业务域组织 Intent，
用 ID 连接跨域变更

Intent Repository

Initiatives / Commerce / Payment / Fulfillment

每个 Intent 有唯一 ID、Owner、状态、关联域与系统

Knowledge Base

Domains / Architecture / ADR / Glossary / Runbooks

沉淀跨需求复用的稳定知识，不复制到每个 Intent

Engineering Repositories

Specs / Plans / Tests / Code / PR / Release

在实际代码仓库中管理可执行工程产物

EXAMPLE · INTENT METADATA
id: PAY-002 title: Partial Refund type: capability status: approved initiative: INIT-001 domains: - payment - commerce affected_systems: - payment-service - order-service - merchant-portal related_intents: - COM-002

目录按业务域归属；唯一 ID 和显式引用表达关系。不要依赖目录层级推断业务依赖。

08 · CONTROL MODEL

用轻量治理，避免 Intent 库变成新文档债务

01 · Ownership

每份知识有明确 Owner：Intent—Product；领域知识—Domain；架构—Architect；规范—Engineering。

02 · Change impact

变更不仅检查代码和测试，也检查受影响的业务规则、架构文档和引用。

03 · Lifecycle

Intent 从 Draft 到 Approved、In Progress、Done、Superseded；历史保留，不把旧 Intent 当作当前事实。

04 · Knowledge health

AI 定期检查失效链接、重复规则、文档与代码冲突、过期知识和无 Owner 内容。

关键机制：规则发生变化时，创建新的变更记录；当前知识在受控流程中更新；历史 Intent 保留当时的目标与决策。

09 · RECOMMENDED WAY FORWARD

从小范围试点，验证新的工作方式

01

建立最小边界

选一个业务域；定义 Intent 粒度、元数据、状态和 Owner；明确 Intent / Knowledge / Spec 分工。

02

引入 AI Product Agent

先接入一个需求入口；实现知识检索、重复识别、草案生成、问题澄清和审批 Diff。

03

连接工程交付

把 Intent ID 贯穿 Spec、PR、测试和发布；验证上下文传递与知识更新闭环。

目标不是让每个人写更多 Markdown，
而是让每一次业务变化都能被准确理解、可靠决策、持续追溯。

设计原则：Human-driven · AI-maintained · Git-governed
