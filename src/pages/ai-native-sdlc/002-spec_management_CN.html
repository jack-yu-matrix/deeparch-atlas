02 / 参考实践

Claude Academy 建立了 Intent → Spec → Build 模式

Requirements and Design 课程描述了一种实践方式：产品负责人批准 intent.md 后，Claude 在组织 Skills 的约束下生成需求与设计 Spec。产品负责人审阅 AI 的结果，而不是亲自撰写整份文档。

传统软件交付

  • 业务想法由分析人员进行解释。
  • 需求由专门团队整理和形式化。
  • 设计由另一个团队再次解读。
  • 不同阶段反复传递和转换上下文。
  • 政策冲突往往在后期评审时才暴露。

AI 原生软件交付

  • 产品负责人创建并批准 intent.md。
  • Claude 加载 Intent 和组织 Skills。
  • AI 生成编号需求及设计 Spec。
  • 明确标记关注事项和政策冲突。
  • 产品负责人审阅、解决问题并批准。
重要原则： Spec 必须足够完整，能够支撑工程团队开展计划和实施。AI 准备决策材料，但不取代人的审批责任。

03 / Spec 设计

优秀的 Spec 是可执行的决策记录，而不只是设计文档

Spec 应清晰表达问题、需求、设计选择、约束、待确认问题和验证方式，使工程团队能够据此制定计划并开展实施。

需求 Requirements

  • 稳定的需求 ID：R1、R2、R3……
  • 可观察的行为和验收标准。
  • 业务规则和数据需求。
  • 非功能性需求。

设计 Design

  • 系统边界和职责。
  • API、事件及数据合约。
  • 身份认证和访问控制。
  • 性能、韧性和缓存策略。

决策证据

  • Intent 约束及其满足方式。
  • 明确保留的待确认问题。
  • 关注事项及对应责任人。
  • 验证状态和审批状态。
设计规则： 对需求进行编号，使工程计划、代码变更、测试、缺陷和评审意见都能引用同一个稳定的需求标识。
SPEC 设计原则05
03 / Spec 设计

Spec 示例：让需求具备可测试性和可追踪性

示例 / 理赔状态自助查询

需求 Requirements

ID需求描述
R1已登录客户可以查看每笔未结案理赔的状态、下一步操作和预计日期。
R2状态限定为：已接收、审核中、已批准、已付款。
R3响应内容只能包含约定的三个字段。
R4客户看到的状态数据延迟不得超过 60 秒。

设计决策

  • claims-api 提供 GET /claims/{id}/status。
  • 通过 Gateway JWT 进行身份认证。
  • claims-api 从 claims-core 读取数据。
  • Portal 使用 StatusPanel，并采用 60 秒缓存。

已处理的约束

个人信息：响应 Schema 排除标记为 PII 的字段。

身份认证：沿用现有 Gateway JWT，不新增登录或角色。

待确认问题

第三方定损人员是否需要访问？不预设答案，而是作为明确问题保留。

关注事项

安全 定损人员目前没有 Portal 账户。

合规 UX 日期展示与品牌对付款承诺的措辞存在冲突。

性能 claims-core 吞吐量需要进行负载测试。

03 / Spec 设计

在 Spec 进入 Build 之前建立质量准入标准

Spec 完整性

  • 每项需求都有稳定 ID。
  • 每项需求都有验收标准。
  • 明确系统归属和业务归属。
  • 明确依赖关系和接口。
  • 非功能约束具备可衡量指标。
  • 待确认问题不会被悄悄丢弃。

Spec 一致性

  • Intent 约束映射到 Spec 设计决策。
  • 应用架构规范和政策 Skills。
  • API 和事件合约之间没有冲突。
  • 需求之间没有相互矛盾。
  • 每项需求都定义了验证方式。
  • 风险和例外都有明确责任人。
Spec Definition of Ready：只有当完整性和一致性检查通过、未解决问题清晰可见、需要人工决策的事项已交给相应责任人时，Spec 才能进入正式审批。

04 / 企业级挑战

企业级变更很少局限于单一系统边界

一个业务目标可能横跨多个渠道、领域服务、传统平台、数据平台、外部供应商及共享能力。

业务复杂性

  • 一个 Intent 可能影响多个业务能力。
  • 一个业务能力可能跨越多个系统。
  • 业务归属与技术归属并不相同。

技术复杂性

  • 微服务和共享 API。
  • 传统系统与异步事件。
  • 分布式数据归属。
  • 独立部署和发布生命周期。

治理复杂性

  • 安全、合规和架构控制。
  • 多个评审和审批责任主体。
  • 跨团队依赖和变更风险。
反模式： 将业务 Intent 拆成多个彼此独立、按微服务划分的 Intent。这会割裂业务目标，削弱端到端追踪能力。

05 / Intent 与 Spec 架构

通过三种互补的 Spec 保持端到端一致性

业务能力视角

Feature Spec

描述端到端业务能力、用户旅程、业务流程、业务规则和验收标准。

回答的问题：整体解决方案必须实现什么？

跨系统
工程实现视角

System Spec

描述特定系统需要进行的变更，包括数据、行为、组件、依赖和运行约束。

回答的问题：这个系统具体需要改变什么？

系统归属
接口协作视角

定义生产者和消费者共同遵守的 API、事件、Schema 和集成合约。

07 / AI 自动化架构

通过自动丰富上下文减少人工架构文档维护

上下文来源

  • 源代码和代码仓库结构。
  • API 规范及事件 Schema。
  • 服务注册中心和归属元数据。
  • 部署及基础设施配置。
  • 架构决策记录。
  • 现有 Spec、测试和运行证据。
  • 组织 Skills 和政策规范。

上下文丰富后的输出

  • 系统与服务边界。
  • 生产者和消费者依赖。
  • API 和事件关系。
  • 数据归属及敏感性。
  • 技术栈与运行约束。
  • 系统 Owner 和政策相关方。
  • 信息置信度及来源证明。
运营原则：如果信息可以从权威工程系统自动提取，就不要要求团队再手工维护一份重复的架构目录。人负责确认边界、归属和关键决策，而不是反复录入机器可以识别的事实。

08 / 变更驱动自动化

只重新生成发生变化的内容：Spec 增量演进

一个 Intent 的变化应该触发基于图谱的影响分析，而不是重新生成所有下游文档。

Intent 变更提交 / 已批准更新
→
语义 Diff新增、修改、删除的需求
→
影响分析遍历受影响的图谱节点
→
选择性更新仅重新生成受影响的 Spec
→
评审与验证检查变更和证据

变更影响逻辑

新增需求 → 识别受影响的 Feature、System 和 Contract Spec。

修改需求 → 计算下游依赖及回归测试范围。

删除需求 → 识别可能失效的设计、代码和测试，交由审核。

生成上下文版本化

记录 Intent 版本、需求版本、系统上下文版本、Prompt 版本和 Skills 版本。

保留 Spec 变更原因以及本次重新生成范围的证据。

预期成果：减少无意义的重复生成、无关评审变更和 PR 噪音，提高变更影响分析的可靠性。

09 / 自动化质量保障

在生成阶段和仓库级别使用同一套验证引擎

Hook 提供即时反馈，CI 提供仓库级质量门禁。两者应调用同一验证器，而不是维护两套重复规则。

生成阶段 Hook

快速反馈
  • 在 Markdown Write 或 Edit 后触发。
  • 验证当前文档语法和元数据。
  • 检查直接链接及目标 ID。
  • 将错误反馈给生成 Agent。
  • 允许受控自动修复并重新验证。

仓库级 CI

合并质量门禁
  • 验证所有变更节点及受影响节点。
  • 检查失效链接和重复 ID。
  • 检查图谱一致性和反向链接。
  • 检查必要的追踪覆盖率。
  • 对定义的严重问题阻止合并。
实现模式：Claude Code Hook → knowledge-graph-validator → 可执行的验证报告 → Agent 自动修复 → Git PR → 仓库级 CI → 合并审批。可以使用 Stop Hook 做最终检查，但必须防止无限重试循环。

实现参考：Claude Code Hooks 官方文档。

10 / 评审上下文工程

在要求人做出决策前，先准备好完整评审材料

评审工作经常消耗在寻找上下文、对比文档和发现依赖关系上。AI 应自动准备这些证据。

变更摘要

  • 变更了什么，以及为什么变更。
  • 哪些需求发生了变化。
  • 哪些内容新增、删除或被替代。
  • 哪些 Spec 和合约被重新生成。

影响证据

  • 受影响的系统和服务。
  • 上游及下游依赖关系。
  • 潜在回归测试范围。
  • 政策和架构检查结果。

待决策事项

  • 需要决策的待确认问题。
  • 相互冲突的约束和备选方案。
  • 风险等级和信息置信度。
  • 建议责任人和审批路径。
评审原则：不要让评审者自己重新拼凑事情的来龙去脉。将变更、证据、未解决决策和潜在影响集中在一份 Review Context Package 中。

10 / 人类治理

根据风险和决策权限路由评审，而不是根据文档数量

低风险

自动化保障

处于已批准模式内、成熟且可逆的变更。

示例：文档更新、低影响配置变更及常规兼容性 Schema 变更。

控制：自动化检查和正常团队流程。

中风险

责任人评审

影响范围明确、局限于部分系统或运行环节的变更。

示例：API 行为变化、数据转换和跨服务依赖。

控制：相关 System Owner 或 Technical Lead 批准。

高风险

正式决策

涉及重大安全、合规、架构或业务风险的变更。

示例：身份模型变更、敏感数据使用及重大领域边界调整。

控制：指定政策负责人或架构委员会批准。

不可妥协的原则：AI 可以分类风险、推荐评审人和准备证据，但不能越权批准例外，也不能接受超出其授权范围的风险。
基于风险的治理19
11 / 持续一致性管理

通过持续漂移检测保持 Spec 与实现一致

Spec 并不会在批准后就失去价值。它始终代表预期行为，必须持续与不断演进的实际实现进行比较。

漂移信号

  • API Schema 与 Contract Spec 不一致。
  • 代码行为不再满足某项 Requirement。
  • 测试不再验证要求的验收标准。
  • 部署配置违反设计约束。
  • 服务依赖关系发生变化。
  • 政策或 Skills 版本已经更新。

漂移处理流程

  • 检测并分类差异。
  • 判断是设计变化还是实现变化。
  • 分析受影响的需求和下游节点。
  • 建议更新 Spec 或修正实现。
  • 将重要决策交给对应责任人。
  • 记录证据及获批的解决方案。
关键区别：绝不能仅仅为了匹配现有代码，就自动重写 Spec。必须先判断是实现偏离了已批准设计，还是预期设计本身发生了合理变化。

14 / 技术蓝图

从轻量级的 Git 原生架构开始

推荐基础技术体系

  • 知识载体：Markdown + YAML 元数据。
  • 版本管理：Git 仓库和 Pull Request。
  • 验证：由 Hook 和 CI 调用统一 Python 验证器。
  • Agent 编排：Claude Code、Skills 和专业化 Subagents。
  • 上下文：源代码仓库、OpenAPI、服务注册中心和架构记录。
  • 可视化：Mermaid、Obsidian 和 MkDocs。

按需扩展的能力

  • 元数据查询：PostgreSQL 管理结构化图谱关系。
  • 企业服务目录：Backstage 或同类服务目录。
  • 图谱分析：查询复杂度足够高时引入图数据库。
  • 可观测性：CI 遥测、漂移报告和覆盖率仪表板。
  • 治理：审批记录、政策版本和审计证据。
架构原则：不要仅仅因为方案叫 Knowledge Graph 就立即引入图数据库。第一阶段使用稳定 ID、元数据、相对链接和自动仓库扫描即可。只有当规模和查询需求真正需要时，再增加基础设施。
